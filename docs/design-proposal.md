# 智能任务总体方案

本文定义产品目标与架构选择，不把目标当作验收证据。实际实现见[技术设计](technical-design.md)，验证范围见[验证说明](validation.md)。

## 1. 产品目标

Agent Task 是独立的智能任务调度与管理系统：

- 用户提交以 Prompt 为核心的目标，可立即、定时或周期执行，并限制截止时间。
- 每次任务实例有独立的协调会话，理解目标、制定执行计划、解释中间结果、处理澄清并组织交付。
- 具体分析、编码、研究和工具操作交给 ACP 执行端，以 Pi Agent、Codex、OpenCode 等为集成目标。
- 保存任务、执行、会话、计划、交付和失败事实；不依赖发起客户端或浏览器持续在线。
- 协调员只能在管理员授权范围内委派，不自动批准权限、猜测关键用户意图或重放结果不明的操作。
- 长期提供独立 HTTP 管理页面；首期只提供 MCP 管理接口，不实现页面。

当前处于调研阶段，直接修改当前接口和数据结构，不做兼容、业务库版本递增或迁移。旧数据保留，普通启动不迁移或删除。只保留基础、关键正确性和安全边界测试。

## 2. 架构选择

```text
          MCP 客户端 / 后续页面
                  │
             任务管理服务
       时间计划、准入、状态与监督
                  │
          pi durable 协调员
        每个 TaskRun 独立会话
       理解 → 计划 → 委派 → 验收
                  │ 受控工具
            ACP 执行服务
                  │
     Pi Agent / Codex / OpenCode
         各自原生模型与领域工具
```

Pi durable 提供现成模型循环、会话持久化、工具检查点、收件箱、任务状态机和观察能力。平台不重写这些机制。它仍是实验性 SDK，需要固定版本、明确存储契约和升级过程。

外层时钟只决定何时开始 TaskRun；协调员决定本轮节点派发。不得让旧固定 DAG 调度器与协调员同时推进同一节点。

协调员与执行端分工：

| 事项 | 协调员 | 确定性服务 | ACP 执行端 |
| --- | --- | --- | --- |
| 理解目标、计划、澄清、语义验收 | 负责 | 校验结构和状态 | 报告事实和问题 |
| 调度、预算、截止、取消 | 遵守 | 强制执行 | 响应取消 |
| 领域推理和业务工具 | 委派 | 不实现领域逻辑 | 负责 |
| 权限 | 不授予 | 可控入口检查 | 原生操作入口约束 |
| 持久状态和恢复 | 使用记录 | 决策及可靠提交 | 保留自身业务证据 |
| 结果不明 | 不重新派发 | 阻塞并核对 | 提供可验证状态 |

协调员不默认持有 Bash、任意文件写入或执行端凭据。通过窄能力使用注册执行端、读取本轮材料和提交验收。技能、角色、Prompt 和工具描述不是授权。

## 3. 领域模型

- **Task**：目标、执行端授权范围、计划、截止、预算及配置快照。
- **TaskRun**：一次时间槽的运行，有独立协调会话和执行记录。
- **NodeRun**：一个计划节点的执行身份，可在同一个 ACP Session 内澄清多轮。
- **协调 Conversation**：模型上下文和推理/工具调用历史，不能替代业务状态。
- **ACP Session**：执行端会话，不能等同于任务或外部业务账本。
- **Delivery**：明确接受的交付内容和来源，独立于聊天记录。

单节点和多节点任务使用同一 API 和执行路径。计划是 DAG，依赖边只允许传递本轮已接受的直接上游交付。并行分支可使用不同执行端。

首个研究版本由协调员生成并提交一次固定计划。执行中改计划、追加节点、独立重试等能力不默认开放，避免以改计划绕过不确定执行边界。以后如需支持，应定义可变范围、节点身份和副作用规则。

## 4. 完成与交互

协议完成、节点交付、整轮完成分别表达：

1. ACP end_turn：执行端结束一轮响应，可能是问题或拒绝。
2. 协调员审阅：已有上下文足够时继续同一会话，不足时保存具体问题并进入 waiting_input。
3. 接受交付：服务保存来自执行端的明确交付及验收理由，才允许下游消费。
4. 完成 TaskRun：必要节点全部交付，协调员明确提交最终声明。

不能根据问号、固定关键词或 end_turn 自动判断业务成功。模型验收也可能误判；结构、来源和权限由代码校验，领域正确性需要可验证证据。高风险操作不能依赖协调员自报成功。

无人值守运行不等待交互式权限批准。缺少用户事实时持久等待，有独立期限；人工回复续接原 TaskRun 和协调会话，保留已完成工作。ACP 会话只短时保留，丢失后停止并要求核对外部结果，不能用回复重发旧操作或扩大权限。

## 5. 持久性与副作用

业务账本与协调日志分开：前者是派发和完成事实的唯一来源，后者保存模型上下文、工具记录和恢复检查点。不能双向复制状态后让两份记录各自决定是否执行。

必须先保存派发意图，再启动外部工作。两库和外部进程没有天然跨系统事务，依靠稳定 TaskRun/NodeRun 身份、固定协调提交 ID、明确恢复核对处理崩溃窗口。

- 协调模型请求可从已提交上下文重发，不等于恢复原内部推理，也可能再次收费。
- durable 的 replay=unsafe 阻止同一未完成工具调用重放，但不能阻止模型发起新调用；业务入口必须阻止重复派发。
- 原 ACP 会话丢失时，不自动创建新会话来假装继续旧执行。
- 有可靠已提交交付且没有活动 ACP 会话时，协调流程可以继续。
- 未知结果必须停止，不能自动切换执行端、恢复聊天后重发副作用或删除失败历史。
- 取消停止后续动作，不撤销已经发生的外部操作。

工作流幂等不能证明外部交易、提交或部署只发生一次。需要自动重试的领域，必须先有外部幂等键和查询核对协议。首期不用于无人值守交易。

## 6. 生命周期与管理

平台独立运行，客户端断开不取消任务。systemd 可负责开机启动和进程组清理，用户注销后的运行需显式配置 lingering。关机或休眠期间不保证准点。

Task 的暂停/恢复/取消控制未来时间槽；中止当前 TaskRun 是独立操作。恢复不补跑已消费或过期的时间槽。同一任务前轮未结束时跳过后续槽，避免周期重叠。

正常停服先停止新派发，再中止运行、关闭 SDK/进程/存储并释放排他锁。中断的外部工作保留未知事实。不能把一个进程内的恢复保证推广为跨机分布式保证。

## 7. 权限、资源和集成

执行端由管理员注册本机命令、固定目录、环境引用、读取范围及无人值守确认。普通任务请求不能传任意命令、凭据或 MCP 地址。

ACP 请求审批是可选能力，白名单不是完整授权或沙箱；不申请审批的 Bash、网络、文件和 MCP 工具仍由执行端原生策略约束。平台服务 token、协调模型凭据与执行端凭据分开。

执行端按自己的原生规则加载技能、MCP 和配置。首期不提供技能上传、动态 MCP 转发或个人聊天复制。执行端的私有工具和业务记录不能通过转交其他 Agent 绕过授权限制。

后续页面调用同一业务服务，提供任务/运行/计划/交付/问题管理。上线前独立设计认证、CSRF、输出渲染及受控文件下载；不能移除 Origin 校验就当作完成安全页面。

## 8. 实施与验收

首先验证一个完整闭环：目标 → 协调计划 → 真实 ACP 会话 → 问题澄清 → 接受交付 → 完成声明。然后验证串行、并行汇合、缺信息、取消、认证失效和中断不重复派发。

本地不使用假模型或模拟 provider 证明闭环。基础测试验证真实存储、SDK、进程及结构化状态契约；真实模型和各执行端使用获准环境独立验收。

未纳入首期：丢失 ACP 会话的重连及人工核对后恢复、已提交计划动态修改、自动重试/故障转移、远程执行、多租户、日历时区调度、技能同步和 HTTP 页面。它们是独立产品决策，不因引入 durable 自动获得。
