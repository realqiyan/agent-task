# 架构原则

目标：让维护者可以局部理解和安全修改系统，不必先掌握全部实现。本文定义持续开发的架构要求；[总体方案](design-proposal.md)定义产品边界；[技术设计](technical-design.md)记录实际实现与尚未收敛的差距。

## 1. 明确责任

按业务含义和变化原因划分模块。每条规则、每份状态只有一个责任归属。共同变化的内容放在一起，独立变化的内容保持分离。

- 工具拥有输入、输出、schema、错误契约和调用适配。
- 服务拥有业务决定、状态转换、授权策略和副作用顺序。
- 存储拥有严格读写、事务、索引和持久化健康状态，不决定何时重试、跳过或恢复业务。
- 接入拥有 MCP/ACP、进程和操作系统协议，不另写一套调度或批准规则。
- 应用层拥有启动、关闭、运行实例及资源生命周期。
- UI 只呈现状态、收集操作，不直接改存储或授予执行权限。
- 数据模型只描述 Task、Run、执行配置和事件，不放业务行为或 SDK 对象。

服务接收普通数据与窄能力，不接收完整 MCP 请求上下文、ACP 连接、HTTP 对象或子进程对象。

## 2. 保持产品边界

平台使用 pi durable 为每个 TaskRun 运行独立协调会话，理解目标、提交计划、处理澄清并验收结果。实际分析、编码、研究和领域工具由 ACP Agent 完成。复用 SDK 模型循环，不增加第二个规划器或与协调员竞争的节点调度器。

协议 turn 结束、接受交付、完成整轮是不同事实。问题和拒绝不能自动作为下游交付。确定性服务负责授权、预算、完成前提和结果不明时的停止；模型不得绕过这些入口。

优先使用官方 MCP/ACP SDK、执行端原生会话、认证、技能、工具和操作系统进程管理。协议能力协商与执行端行为分别验证，不能把所有实现强行归一为能力最少的交集，也不能假定声明能力就代表已验收。

Pi Agent、Codex、OpenCode 是通过 ACP 执行端适配接入的目标。核心不导入某个执行端的内部业务服务，不读取其私有存储格式，不把特定领域的业务规则泛化为平台规则。

角色、专业方法和执行说明属于执行端资料或技能；不得因研究方法变化而修改平台调度代码。技能和提示词不授予权限。

## 3. 分层与目录

按责任形成以下依赖，而不是按文件名制造层次：

```text
main / app：装配与生命周期
  ├─ tools / ui ────────────────┐
  ├─ integrations：协议与进程  │
  └────────────────────────────▼
                         services
                         ↙      ↘
                     model     storage
```

服务定义窄执行能力，接入实现它，由入口装配。图中的接入不意味着服务可以导入完整接入实现。

| 层 | 目标责任 | 当前 MVP 对应代码 |
| --- | --- | --- |
| `main.ts`、`app/` | 装配、HTTP 生命周期、服务实例启停 | `main.ts` 及 tasks 中的服务生命周期 |
| `tools/` | 完整 MCP 工具契约、输出和执行适配 | `mcp.ts`、`task-contract.ts` |
| `services/` | 任务、调度、执行、授权等业务规则 | `tasks.ts`、`human-input.ts`、`permissions.ts` 及 model/results 中的相关规则 |
| `model/` | 数据类型，不含状态转换或 SDK 类型 | `task-model.ts`、`model.ts` 中的数据定义 |
| `integrations/` | durable 协调接入、ACP、MCP transport、worker IPC、进程与 flock | `coordinator.ts`、`acp.ts`、`node-execution.ts`、`worker.ts`、`lock.ts` 及 main 中的接入代码 |
| `storage/` | SQLite、配置文件、持久 schema、可靠提交 | `task-storage.ts`、`coordinator-storage.ts`、`config.ts`、`results.ts` 中的读写与校验 |
| `common/` | 确实跨领域共享的时间格式、错误等纯辅助逻辑 | `model.ts` 等文件中的通用辅助函数 |
| `ui/` | 后续 HTTP 页面和展示适配 | 尚无实现，不提前建空目录 |
| `tests/` | 对应领域的具体风险验证 | 当前为顶层 `*.test.mjs` |

这些是职责归属，不是要求立即建立所有目录。模块较小时可保留集中入口；一个文件承担多个独立变化原因时再拆分。层内按领域聚合，不为目录对称创建空模块。

当前实现不是已完成的分层样板。涉及现有跨层职责的功能修改应连同对应边界收敛，不继续让新界面直接调用存储。结构调整要保持公开行为与测试有效；没有需求时不做纯目录搬迁。

## 4. 限制依赖

- 工具、命令和未来页面调用同一服务，不因入口不同绕过授权、并发、截止检查和持久化。
- 服务可以依赖 model、storage 和纯辅助逻辑；不得依赖 UI、durable/MCP/ACP SDK 或应用入口。普通输入数据契约可共享，协议适配不可反向依赖。
- 接入层可以引用服务定义的类型和窄能力，不创建业务服务或决定业务恢复策略。
- 存储不反向依赖服务、工具、接入、UI 或应用入口。数据库事务由存储执行，事务中允许的业务变更由服务决定。
- model 不依赖其他业务层或 SDK。边界 schema 放在所属工具或存储旁，不把所有验证塞进一个全局模型文件。
- 实现显式装配，避免循环依赖、全局可变状态和依赖服务定位器。

只为已有变化点定义窄策略。新增一种真实协议或执行器差异时扩展对应适配；不建立动态插件发现、通用编排平台或大量尚无人使用的接口。

分层落实后使用依赖检查保护边界与循环依赖。当前 `npm run check` 仅检查 TypeScript；不得将其描述为已提供依赖边界检查。不要用测试断言目录或源码文本代替依赖检查。

## 5. 状态与副作用

任务定义、调度游标、Run、Agent Session 和外部业务记录各有责任主体，不能混成一套会话状态。

先可靠保存接收或派发意图，再触发外部执行。相同提交和时间槽必须能够核对，但不把平台去重等同于外部业务幂等。数据库写入、进程启动和远端操作之间没有天然的跨系统事务。

- 取消阻止后续动作，不回滚已发生的副作用。
- 截止时间限制新执行开始，执行超时是独立规则。
- 客户端断开不等于取消任务。
- 服务恢复不等于恢复模型推理，更不等于重发可能已执行的操作。
- 未收到结果不等于没有执行。中断、结果不明、明确失败分别表达。
- 自动重试、补跑和跨 Agent 故障转移必须有已确认的业务安全依据，不能因实现方便默认启用。

资源的创建、使用、失效和释放归属明确。关闭幂等，先停止新派发，再处理活动执行、等待子进程、关闭网络与存储，最后释放所有权。失效的实例或引用不能转用到新的运行实例。

单写入者锁、SQLite 事务、worker 监督和 systemd cgroup 分别解决不同问题。不得用其中一项宣称已经获得跨机一致性、无孤儿进程或宿主隔离。

## 6. 权限与能力

分开保存或展示：

1. 执行端声明和发现的能力；
2. 管理员授予的权限；
3. 某次实际验证的证据。

ACP 连接成功、工具类别、名称和描述都不是授权。预注册执行配置不能由普通任务请求任意改成新的命令、目录、凭据或 MCP 地址。

授权必须在可控制的实际操作入口检查。ACP 审批回调只能约束经过该回调的操作；工具通知、提示词和 `unattendedApproved` 都不能替代工具发送入口、执行端原生策略或 OS 隔离。

后台任务不等待交互式人工批准。不明确允许、元数据不足或授权失效时，拒绝当前请求；不自动选择“永久允许”，不退回更宽权限。取消、恢复、资源传递和 Agent 委派不扩大授权。

客户端服务 token、协调模型凭据与执行端模型凭据分开。凭据通过受控环境或原生认证引用，不进入任务、日志或普通配置快照。输出可能包含敏感资料，限制访问与保留范围，不声称已经全面脱敏。

## 7. 存储与升级

公开协议、配置和持久数据都是契约。严格加载当前支持的契约；未知或损坏数据拒绝使用，不猜测默认值修复历史事实。当前处于调研和 MVP 验证阶段，不维护旧接口、旧格式或独立任务兼容层；单节点和多节点任务统一使用任务模型。移除兼容代码不授权删除用户数据。

发布版本以本项目 `package.json` 为准，不继承其他项目的存储标记或与其捆绑发布。当前数据结构见技术设计。调研阶段直接修改当前结构，不维护业务库格式版本号，不为功能修改增加版本升级流程。

新数据库初始化与既有数据升级分开。实际升级放在独立脚本中，声明源与目标格式，要求停止服务和取得排他所有权，变更前备份，变更后验证，并支持中断后显式接续。普通启动不静默迁移，不为了恢复服务删除任务历史、用户产物或外部业务记录。

不引入文件哈希验证。不以删除失败状态、重建用户工作区或重放外部请求修复记录。容量限制和保留策略应显式说明，不自动丢弃尚未确认保存的证据。

## 8. 验证具体风险

使用 `node:test`、`node:assert/strict`、真实文件、SQLite、进程和协议 SDK。调研阶段只保留最基础、最关键的授权、状态转换、可靠提交、故障停止、取消和恢复测试，不追求覆盖率数字，不断言文档、提示词措辞、UI 标签或文件结构。

不使用 mock、stub、假模型、模拟 provider、个人凭据或真实交易证明正确性。结构化输入与输出可以验证其逻辑契约。真实退出或挂起进程用于验证进程故障，不伪装成 ACP 成功执行。

真实模型、外部服务、不同 Agent 适配器和操作系统部署需要获准环境验收。文档将声明支持、代码实现、本地验证、真实验收分开，保留剩余缺口。不得通过降低权限或存储要求换取测试通过。

## 9. 文档与独立迭代

- README：安装、操作入口、当前能力和关键限制。
- design-proposal：原始需求、总体方案、选型理由及后续能力边界。
- architecture-guidelines：稳定的设计与开发要求。
- technical-design：当前实现、实际模块、数据契约和已知架构差距。
- validation：已有证据和未验收范围。
- AGENTS：维护者入口、开发命令与关键禁区。

每份文档维护自己的主题，其他位置链接，不复制整段规则。需求和方案文档不是历史聊天转录；不同版本通过 Git 查阅，不另留过期方案副本。

仅在使用方法、业务行为、接口或架构边界变化时更新相关说明；不因每次内部细节或 UI 外观调整改写总览。运行时提示词与说明文档分开，技能只保留无当前对话上下文的执行者需要的信息。

本项目可独立阅读、构建、测试、部署和发布。维护不要求同时检出其他项目，也不要求访问产生需求的会话。外部集成通过明确版本和协议契约协作。
